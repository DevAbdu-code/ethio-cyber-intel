# Stage 10 integration, optimization, and reliability report

## Findings and root causes

1. **Correlation repeated per-article feature extraction per pair.** On `n` articles, regex/entity/token/normalization work was repeated inside every one of `n(n-1)/2` comparisons. Pairwise scoring remains quadratic, but most feature work is now performed once per article.
2. **Candidate persistence opened a transaction/connection per result.** Candidate-heavy batches incurred repeated SQLite setup and locking. Results are now saved in one transaction while keeping append-only assessment rows, duplicate checks, and human-review protection.
3. **Collection had avoidable resource and failure coupling.** Each source could allocate its own HTTP session without explicit close, and an unexpected item normalization exception could discard the rest of that feed. Collection now shares/closes its owned session and skips only the malformed item; feed-level failures remain isolated.
4. **Processing states conflated distinct cases.** Optional extraction rejection was indistinguishable from no extraction attempt (`not_available`), and a missing-language fallback method (`not_detected`) could be counted as an assessed Unknown. Rejected extraction now has `extraction_rejected`; the dashboard counts `not_detected` as pending and reserves assessed-Unknown for actual detection results.
5. **Summary status was absent from the processing overview.** A latest-summary status query and explicit created/unavailable/not-generated counts are now shown. Successfully saved summaries trigger a rerun so status counts refresh immediately.

## Integration flow and safeguards

The exercised flow is mocked RSS fetch → per-entry normalization and publication-date preservation → temporary SQLite insert and URL deduplication → language output → pending classification → pending severity → cross-language candidate correlation → extractive summary → dashboard data queries. One timed-out feed does not block two successful feeds. Invalid/missing dates remain `None`; reports retain source and URL. The integration test uses DEMO disabled and a temporary database, then checks database and foreign-key integrity. No real source was fetched in this Stage 10 test.

Feed URLs and redirect targets must use HTTPS and cannot contain URL credentials or obvious localhost/private literal IPs. Redirect hops are bounded and validated before another request. Article pages are same-host HTTPS, robots-checked, no-redirect requests. Optional extractor exceptions retain the publisher RSS metadata and mark the page body rejected. Feed configuration remains trusted-operator input: DNS names are not resolved to block private-address DNS answers, so configuration must not be writable by untrusted users.

SQLite connections enable foreign keys. Existing migrations/history are unchanged and exercised on temporary stores. The configured research database was inspected read-only; no migration or write was issued in this stage. Backup/restore steps are in [installation](installation.md).

## Correlation performance experiment

**Environment:** repository `.venv`, Python 3.14.10; local CPU; machine model and memory were not recorded. **Dataset:** deterministic synthetic in-memory reports generated by `scripts/benchmark_correlation.py`; no database, network, or real intelligence. Both versions use the identical corpus generator, language distribution, and pair scoring rules. The pre-change implementation was loaded from the parent Git revision and each size was timed three times. The optimized implementation was timed three times using the checked-in benchmark; reported values are medians. Candidate counts matched on every repetition.

| Articles | Pair count | Before median (s) | After median (s) | Approx. speed-up | Candidate count, both |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 40 | 780 | 0.217869 | 0.031005 | 7.03× | 119 |
| 100 | 4,950 | 1.420898 | 0.171169 | 8.30× | 807 |
| 300 | 44,850 | 13.038624 | 1.555743 | 8.38× | 7,457 |

These are local microbenchmark observations, not service-level guarantees. They demonstrate unchanged candidate counts on this fixture and reduced runtime for in-memory candidate generation. The score, evidence, status, and threshold logic were not changed. Database batch-persistence time, memory/RSS, larger-scale behavior, and dashboard latency were not independently benchmarked. Pair comparisons remain quadratic; 300 articles is still the operational cap.

Reproduce with:

```bash
source .venv/bin/activate
python scripts/benchmark_correlation.py --sizes 40 100 300 --repeats 3
```

## Security and reliability notes

- URL syntax and redirect validation block common unsafe configured targets, but DNS rebinding/private DNS resolution is not addressed. This local application is not a hardened SSRF boundary or multi-user service.
- RSS feed requests still depend on network/DNS and publisher availability. Responses are bounded by timeouts and configured entry caps; malformed items are isolated. No content-size cap is currently enforced.
- Article extraction fails closed when robots access cannot be checked or denies access, or when identity, host, HTTPS, canonical URL, or explicit-body validation fails. A robots.txt HTTP 404 is treated as no published rules. RSS source/title/date/link remain preserved.
- SQL values use parameter binding; joins and table names are static. `PRAGMA foreign_keys=ON` is enabled per connection. UI content is rendered by Streamlit components; no `unsafe_allow_html` was added.
- No dependency was added. `pip check` checks package compatibility but is not a vulnerability audit. No full dependency CVE scan, deployment penetration test, or DNS/SSRF adversarial test was performed.

## Remaining limitations

- Cross-language retrieval still compares every pair and depends on shared IDs/entities for cross-language candidates; the optimization does not add semantic understanding.
- Rule-based language/category/severity outcomes remain preliminary and do not have independent real-world evaluation data.
- Live RSS connectivity is time-dependent. This integration run is entirely mocked; it makes no new claim about current feed availability.
- Extraction rejection is a broad status, not a categorized reason code. Publisher HTML changes can cause safe fallback to RSS description.
- Streamlit remains local single-user software. Authentication, authorization, concurrent multi-user workloads, scheduled refresh, and high-volume data stores are out of scope.
